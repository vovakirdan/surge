# Runtime V2 Debt Ledger

This is the durable debt ledger for Runtime V2 work. Add new debt here when it
is discovered. Close debt only with evidence: commit, task, command, or linked
document.

## Rules

- Do not hide debt in `NOTES.md` only. `NOTES.md` is a handoff log; durable debt
  belongs here.
- Every debt item must have an owner: an epic, task, or explicit future
  decision point.
- Every runtime task must state whether it touches any open debt item.
- Closing debt requires evidence and a dated note.
- Raising a legacy LOC ceiling in `.loc-legacy-allowlist` is a debt decision and
  must update this file or the owning task evidence.

| RV2-DEBT-022 | Narrow, pre-existing latent lost-wakeup window in the external-await (`done_cv`) compatibility path, found by Epic 8 Task 10's Global-Rule-2 wakeup trace. `mark_done` reads `ex->done_waiters` locklessly in `mark_done_needs_control` (`rt_async_state.c:1496`) to decide whether to take the control lane, and broadcasts `done_cv` only under that lock when the decision took control (`:1567-1569`). The external awaiter (`rt_task_await` workers>1, `rt_async_task.c:337-357`) takes `ex->lock`, increments `done_waiters` (`:343`), then loops `while (task_status_load(target) != TASK_DONE) pthread_cond_wait(&ex->done_cv, &ex->lock)` (`:344-345`) — so its predicate re-check (`task_status_load(target)`) is under `ex->lock`, and `pthread_cond_wait` atomically releases `ex->lock` as it parks. A completion that reads `done_waiters==0` in the window before the awaiter's increment — while the awaited target completes on a worker not re-synchronized with that increment (e.g. an already-`RUNNING` target whose completing thread reads `done_waiters` as a plain, control-free read post-Task-8 and holds no shard lock that pairs with the awaiter's `ex->lock` acquire/release) — can skip both the control acquisition and the broadcast, stranding the awaiter (`done_cv` has no steady-state wakeup source but shutdown). This is the classic StoreLoad / condvar-with-lockless-signaler gap: the awaiter's `increment; load status` and the signaler's `store DONE; load done_waiters` need seq-cst on both sides plus a post-`DONE` re-check that broadcasts under the lock. The simple "increment `done_waiters` before `wake_task`" reorder is insufficient — it closes only the *parked*-target case (`wake_task`'s owner-shard-lock release publishes the increment to the worker that later dequeues the target), NOT the already-`RUNNING`-target case (that worker never re-acquires a lock that pairs with the increment before it reads `done_waiters` in `mark_done`). Empirical note (NOT a proof of safety): the window is a few instructions and the external-await path in practice is `main` awaiting a long-lived task that runs ~the whole program, so the no-keepalive completion-pin TSan stress and the `WorkerAwaitVsExternalAwait` behavior test have never triggered it across the epic — but the ordering gap is real per the memory model and must not be treated as closed. Pre-existing since Task 8 made completion control-free; Task 10 makes NO `done_cv` behavior change (only re-tags the counted acquisition), deliberately avoiding a narrows-but-does-not-close half-fix. | Open | A focused external-await/compat fix, or Epic 8 Task 14 closeout (decides code-vs-carry-forward) | The external-await handshake uses a seq-cst StoreLoad protocol (or an equivalent proven ordering) so a completion cannot skip the `done_cv` broadcast for a parked awaiter, with a focused test, or Task 14 records an explicit carry-forward with rationale. |
